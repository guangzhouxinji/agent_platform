## 4. P1 实现偏差

### IC-P1-01：状态变更入口绕过进入条件和责任来源

- 证据：`TaskChange` 直接携带完整 `subTasks/objectVersions/dependencyVersions`；`PatentTaskCommandService.nextSnapshot` 原样接受并聚合。调用方可以删除子任务、改变 primary、直接写 `COMPLETED` 或替换原因，核心没有验证前态、进入/退出条件、完成依据或状态决定责任来源。
- 设计：`docs/38` 4 要求状态进入/退出条件成立，状态变化保存原因、前后版本、责任来源和相关执行/证据，模型或提示词不能单独写完成状态。
- 问题：当前实现是“调用方提交新快照”，不是受规则保护的状态转换核心。聚合算法正确不能弥补子任务状态来源不受控。
- 影响：后续编排、模型或适配层只要取得调用入口，即可绕过证据/确认条件把任务写成完成或静默移除子目标。
- 分类：代码错误 + 测试不足。
- 修正准入：以受限变更意图和明确责任来源替代整表覆盖；验证子任务身份连续性、合法状态进入条件及完成状态写入边界，并补负向测试。不得自行实现尚未准入的专业充分性规则。

### IC-P1-02：恢复点不完整，恢复没有校验恢复点依赖

- 证据：`RecoveryPoint` 只保存任务版本、子任务、旅程步骤、一个依赖 map 和待办引用；没有已提交产物、失败执行、待重试命令、目标/事实/范围版本的明确承载。`resume(command, subTaskId)` 只确认恢复点存在，随后直接把子任务改成 `IN_PROGRESS` 并清空失败原因/恢复点；取消恢复也直接重新聚合旧快照。
- 设计：`docs/38` 4.2 要求恢复点保存失败前版本、步骤、目标/事实/范围、已提交产物、未完成动作、失败执行、待重试命令和依赖版本；恢复须重验权限、来源、依赖，只重做未提交或失效动作。11.1 还要求恢复校验数据用途、版本与保留有效性。
- 问题：命令可以传空依赖 map，恢复逻辑没有用恢复点依赖做强制比对，也没有来源/用途可用性结果或停止请求承载。
- 影响：依赖变化后仍可在旧失败点继续；取消后可能无条件恢复；无法证明没有全量或错误重跑。
- 分类：代码错误 + 测试不足。
- 修正准入：补足当前切片所需的逻辑恢复引用和恢复校验端口；未知来源、用途、保留结论必须拒绝/暂停，不能填默认值。测试须覆盖依赖变化、权限变化、来源不可用和仅重启未完成动作。

### IC-P1-03：迟到命令没有保留到达事实，事件不足以审计重放

- 证据：旧版本在 `TaskCommandValidator.validateVersions` 直接抛错；仓储只在成功提交后 `record` 命令，失败/迟到路径不保存任何到达记录。`TaskEvent` 也没有 outcome、引用对象版本、关联产物或失败/冲突详情。
- 设计：`docs/38` 11.1 要求迟到确认、选择、工具结果和人工回流保留到达事实；所有变更事件至少表达动作、命令、前后版本、责任来源、依赖、关联产物、结果和时间。
- 问题：当前“迟到命令测试”只断言 `VERSION_CONFLICT`，与“保留到达事实”不是同一能力。
- 影响：无法审计迟到输入为何未成为当前产物，也不能在取消竞态或恢复时重放实际到达顺序。
- 分类：代码错误 + 测试错误（测试名称/结论过度声明）。
- 修正准入：冲突与拒绝也形成不可变命令到达/处理结果记录，但不得生成新产品任务版本；补事件完整性和重启后审计测试。

### IC-P1-04：fingerprint 未绑定实际变更载荷

- 证据：`TaskCommand.payloadFingerprint` 由调用方直接传入；`sameCommand` 只比较该字符串。实际 `TaskChange`、恢复子任务 ID 等不参与计算或一致性验证。相同 identity/key/fingerprint 配不同 `TaskChange` 会直接返回第一次结果。
- 设计：`docs/38` 11.1 的 fingerprint 用于判断实际载荷是否相同；相同命令/键但不同载荷必须冲突。
- 问题：现有测试只把“不同载荷”模拟为不同 fingerprint，没有验证 fingerprint 与真实命令载荷相符。
- 影响：调用方错误或恶意复用 fingerprint 时，不同业务变更被误判成幂等重放。
- 分类：代码错误 + 测试不足。
- 修正准入：在可信边界基于规范化逻辑载荷生成/验证 fingerprint，或由统一命令对象自身封装不可分离的载荷摘要；补“同 fingerprint、实际载荷不同”负向测试。

### IC-P1-05：受保护对象的 DataScope 要求没有服务端权威来源

- 证据：`TaskCommand.requiredScopeReference`、`snapshot(..., requiredScopeReference)` 由调用参数提供；`ProtectedTaskAction` 原样传给策略。Fixture 策略只比较当前 scope 和这个参数。任务/快照没有服务端绑定的资源 scope 引用，也没有解析端口证明 scope 要求来自权威资源事实。
- 已通过部分：`CurrentAuthorizationContextProvider` 决定当前身份；缺身份/失效/无策略默认拒绝；每个命令和快照读取重新调用 Guard；`untrustedClaimedIdentity` 不参与允许判定；未固化真实角色/组织/scope。
- 设计：`docs/35` DATA-08 和 `docs/38` J01/11 要求最终身份与 DataScope 由服务端决定，不能信任前端自报。
- 问题：身份来源已隔离，但“被访问对象需要哪个 scope”仍是调用方可选字符串。当前测试证明的是“与传入 scope 相等”，不是“与服务端资源 scope 相符”。
- 影响：未来 API 若直接映射该参数，调用方可选择自己拥有的 scope 作为要求，权限守卫无法证明任务归属和资源范围。
- 分类：权限边界代码缺口 + 测试不足；由于当前没有 API/生产接入，定为 P1 而非 P0。
- 修正准入：由服务端任务/资源授权解析端口产生受保护资源要求；外部声明只能作为非权威输入且不得决定策略目标。补伪造 scope、任务归属不匹配和权限变化后的再次解析测试；真实 scope 值继续等待 OQ-AUTH-01。

## 5. P2 问题

### IC-P2-01：对象/依赖版本冲突信息不完整

- 证据：对象或依赖版本冲突只返回 `TaskCommandException.currentVersion`（主任务版本）和包含 key 的文本；没有结构化返回冲突对象及其当前版本。
- 设计：`docs/38` 11.1 要求返回当前版本和需要重新读取/确认的冲突。
- 影响：后续调用方无法可靠区分哪个引用需要刷新，只能解析文本。
- 分类：代码可用性缺口 + 测试不足。
- 修正准入：保持逻辑异常而非冻结 HTTP DTO，增加结构化冲突对象、期望值、当前值和建议重新读取范围。

## 6. 反向重放一：任务核心

固定链路：`创建任务 → 版本变化 → 子任务执行 → 状态聚合 → 失败 → 恢复 → 取消 → 再恢复`。

| 步骤 | 当前实现可推导结果 | 验收 |
|---|---|---|
| 创建 | CREATE 生成 V1；九状态由子任务快照聚合 | 通过 |
| 版本变化/子任务执行 | 任一变更命令在 expected version 正确时生成 V2 | 版本通过；状态变更来源不受控，IC-P1-01 |
| 聚合 | 例如已完成 + 等待确认 + 技术失败唯一得到部分完成 | 通过 |
| 失败 | TECHNICAL_FAILURE 强制带一个 `RecoveryPoint` | 结构存在，但内容不足，IC-P1-02 |
| 恢复 | 权限重验后直接把目标子任务改为进行中并生成新版本 | 未核对恢复点依赖/来源/用途，失败 |
| 取消 | 先提交的取消版本获胜，后到旧版本命令冲突 | 状态/竞态通过；无停止请求/迟到记录，IC-P1-02/03 |
| 再恢复 | 取消任务在权限重验后原样恢复子任务并生成新版本 | 未验证来源、依赖、保留有效性，失败 |

结论：链路可走通不等于契约闭合。版本和聚合正确，但恢复、迟到审计和状态写入边界失败，因此 TASK-CORE-01 为 FAIL。

## 7. 反向重放二：权限边界

固定链路：`无身份 → 默认拒绝 → 测试身份 → 合法访问 → DataScope 不足 → 拒绝 → 权限再次变化 → 重验`。

| 步骤 | 当前实现可推导结果 | 验收 |
|---|---|---|
| 无身份 | Provider 为空，返回 `IDENTITY_MISSING` | 通过 |
| 默认拒绝 | 有有效上下文但无 Policy，返回 `DEFAULT_DENY` | 通过 |
| 测试身份/合法访问 | 服务端 Fixture 身份且 Policy 明确允许，返回授权上下文引用 | 通过；只证明 Fixture |
| scope 不足 | 当前 scope 与传入 required scope 不符，拒绝 | 表面通过 |
| 权限变化/重验 | 下一命令重新读取当前上下文，收紧后拒绝 | 通过 |
| 反向攻击检查 | 调用方把 required scope 改成自己当前拥有的值时，当前 Fixture Policy 可再次允许；没有服务端任务 scope 事实用于反证 | 失败，IC-P1-05 |

结论：当前身份和重验机制成立，但 DataScope 的资源侧权威来源未闭合，因此 AUTH-BOUNDARY-02 为 FAIL。

## 8. 测试真实性检查

18 个测试中的有效覆盖：九状态枚举、聚合优先级、原因分离、同/异 fingerprint、任务/对象/依赖版本冲突、并发先提交者、取消优先、历史快照、基本技术失败恢复、五类命令共用 expected version、缺身份、默认拒绝、上下文失效、策略拒绝、前端身份声明不生效和权限再次校验。

必须补充但当前缺失：

- 同一 identity/key/fingerprint 但实际 `TaskChange` 不同必须冲突；
- 迟到命令/拒绝命令在重启后仍有到达与处理结果记录；
- 恢复点依赖变化、来源不可用、权限变化时不得直接恢复；
- 取消产生停止请求，迟到执行结果不推进当前任务；
- 任意调用方不能直接删除子任务或把子任务写成完成；
- 伪造 required scope 不能改变服务端资源授权要求；
- 本报告两条完整链路应作为组合 Contract Test，而不是分散断言。

因此 `18/18` 仍是有效测试结果，但不能作为两个任务 PASS 的充分证据。
