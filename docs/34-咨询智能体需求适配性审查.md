# 咨询智能体需求适配性审查

审查日期：2026-09-22  
审查对象：`requirements/知识产权咨询助手/*`、咨询 MVP/V0 设计、真实性与调用链审计、当前磁盘源码  
审查性质：只读产品与需求适配性审查，不是实现验收，不改变任何正式需求 D/V/A 状态

## 1. 执行摘要

### 1.1 总结论

**当前材料不足以直接指导 Codex 做出一个真正好用的知识产权咨询智能体。** 但根因不是“原始需求只要求关键词检索或单轮聊天”。相反，原始需求已经明确了统一咨询入口、多意图、缺项追问、上下文来源轮次、用户纠正、对象切换、结果集指代、工具结果进入后续对话、继续追问、检索条件调整、语义召回、重排、证据片段、原文定位、会话恢复和人工边界等重要目标能力。

当前不足由四部分叠加形成：

1. **需求问题**：各模块合同较完整，但缺少贯穿自然语言目标、工具选择、中间结果判断、再次检索、证据充分性判断、停止条件和人工升级的统一任务行为政策。
2. **V0 范围问题**：V0 为验证架构而合理采用单一意图、合成数据、固定技术参考目的和最小对象模型，但这些临时边界长期主导了产品形态。
3. **实现问题**：当前统一入口更接近“无持久会话的意图路由 + 一次工具调用”，还不是能够保持任务状态、根据结果自主深化并完成用户目标的任务型智能体。
4. **验收问题**：已有测试和调用证据能证明链路、模型或检索代码运行过，不能证明检索效果、答案质量、任务完成率或专业可用性。

因此，下一步不应先增加 Agent Runtime、Workflow 平台或继续堆页面，而应先由业务和专业人员确认完整产品能力、智能行为规则、允许数据范围、质量维度及验收样本，再选择实现路线。

### 1.2 核心判定

| 判断项 | 结论 |
| --- | --- |
| 原始需求是否过窄 | 否。目标能力覆盖面较广，但跨模块的任务决策政策不完整 |
| V0 是否过度影响产品 | 是。合理的技术验证收缩已事实性成为当前产品边界 |
| 当前是否有真实能力 | 有。模型意图候选、本地公开专利检索、基于候选证据的模型答复、来源版本复查等是真实执行，但能力较弱或依赖运行配置 |
| 当前是否是任务型智能体 | 否。缺少持久任务上下文、结果集引用、动态计划、迭代检索和任务级结束判断 |
| 当前能否称为专业检索/专业咨询 | 不能。字面匹配、固定权重和开发数据未经过专业效果验收 |
| HTTP 200、页面加载、API 存在、模型调用和测试通过能否证明好用 | 不能。这些最多证明技术链路存在或在特定环境运行过 |

## 2. 审查范围、方法与判定口径

本次逐项审查了咨询助手目录下 16 份原始需求，以及 `docs/01`、`docs/06`、`docs/11` 至 `docs/14`、`docs/17`、`docs/30`、`docs/31` 和当前咨询、检索、对照、模型、知识库相关源码。

重要能力统一按四层判断：

| 层次 | 问题 |
| --- | --- |
| 用户任务 | 用户最终要解决什么问题，而不是要进入哪个模块 |
| 产品行为 | 智能体应如何理解、追问、执行、核验、调整和结束 |
| V0 范围 | 为技术验证临时证明了什么、主动排除了什么 |
| 当前实现 | 当前磁盘代码真正执行了什么 |

状态词含义：

- **需求已明确**：原始需求已给出可执行的产品规则或验收行为。
- **需求部分明确**：定义了模块能力，但跨步骤决策、异常或质量口径不完整。
- **需求缺失**：需要业务或专业人员新增决策，不能由开发推定。
- **V0 主动收缩**：设计明确说明只为技术验证排除，不能外推为最终边界。
- **实现尚未达到目标**：实现方向可保留，但当前能力或闭环不足。
- **实现偏离需求**：当前交互或能力边界与原始目标明显不一致。

本报告不把以下事实当作业务可用性证据：HTTP 200、页面成功渲染、存在 API、有返回结果、模型请求成功或自动化测试通过。

## 3. 原始需求能力地图

原始需求不是一个“聊天框需求”，而是一组较完整的咨询产品模块合同。

| 能力域 | 原始需求已明确的内容 | 完整性判断 |
| --- | --- | --- |
| 统一入口 | 用户通过咨询智能体提出问题，由系统识别意图并路由已授权能力；内部模块不应要求用户理解 | 需求已明确 |
| 意图理解 | 主意图、候选意图、多意图、未知、需澄清、槽位来源轮次、缺失项、路由建议 | 需求已明确 |
| 多轮对话 | 上下文更新、后续更正覆盖槽位、已确认信息不重复索要、冲突和指代不清时追问 | 需求已明确 |
| 结果引用 | 能引用上一轮实际结果集，如“第二个结果”，并将工具结果用于后续对话 | 需求已明确 |
| 对象与目标变化 | 支持对象切换、条件调整、新任务和回答后继续追问 | 需求已明确到交互要求；重新规划政策部分明确 |
| 专利检索 | 技术方案、特征提取/编辑/确认、关键词和语义召回、过滤、多候选、重排、证据片段、原文 | 需求已明确 |
| 商标与案例 | 分别定义检索、对照/参考、来源、过滤与资料库能力 | 需求已明确；专业质量口径仍需确认 |
| 来源与版本 | 来源定位、稳定版本、失败与无结果区分、历史不可覆盖、权限复查 | 需求已明确 |
| 会话运行 | 会话/消息/流程、取消、重连、中断恢复、并发、过期、统计和版本固定 | 需求已明确 |
| 配置治理 | 智能体、提示词、意图和流程的草稿、试运行、发布、回滚、权限与版本 | 需求已明确 |
| 人机边界 | AI 可抽取、分类、总结、分析候选和草拟；不得替代授权人员作正式法律或业务决定 | 需求已明确 |
| 智能任务政策 | 何时再次检索、证据何时充分、冲突结果如何权衡、何时停止或升级 | 需求缺失或分散，未形成统一合同 |
| 业务质量 | 提及准确率、召回率和专家样本，但未形成完整目标值、通过线和责任人 | 需求部分明确；阈值待业务/专业人员确认 |

结论：原始需求对模块、数据、权限、版本和可追溯性约束较强；对“智能体如何连续帮助用户完成目标”的横向行为定义较弱。工程合同不能替代产品决策政策。

## 4. V0 主动收缩能力地图

`docs/11` 至 `docs/17` 明确把首个闭环收缩为“专利相似检索/技术参考”，并排除真实中心、真实模型、完整会话、配置发布、专业效果验收等。该选择适合隔离技术风险，但不构成目标产品定义。

### 4.1 A 类：合理的纯技术验证排除项

| 排除项 | 审查结论 |
| --- | --- |
| 合成数据和内存仓储 | 可用于第一轮领域、状态和来源追踪验证 |
| 合成 V0 不接真实 SSO | 可用于隔离业务身份依赖，但不能作为真实验收环境 |
| 不做正式人工复核流程 | 可先验证 AI 与人工决定边界 |
| 不搭建通用 Agent Runtime / Workflow 平台 | 应继续保持；产品目标不要求先建通用平台 |
| 校准前不输出数值评分 | 合理，避免伪造专业精度 |
| 不做外部通知和回写 | 不影响第一条只读咨询链技术验证 |
| 不预先统一三域证据大模型 | 合理，避免跨域语义过度抽象 |

### 4.2 B 类：暂时排除、目标产品必须恢复

真实授权数据、真实模型通道、语义/混合检索、多候选与原文证据、完整对话生命周期、意图/提示词/流程配置、专业质量评价、查询过滤与迭代检索、工具结果进入后续对话、用户纠正后的重规划、对照交接和最终闭环，均可在 V0 暂缓，但必须回到目标产品路线。

### 4.3 C 类：若继续保留则属于错误收缩

| V0 约束 | 为什么不能成为最终限制 |
| --- | --- |
| 只允许一个意图 | 无法承接用户自然表达的复合业务目标 |
| 所有问题固定为技术参考目的 | 会丢失用户真实目的，且掩盖需要确认的风险边界 |
| 一次固定工具顺序 | 无法根据中间结果决定补问、扩大/收窄范围或继续取证 |
| 每个下一步都由用户手工选页面 | 把内部工具结构变成用户任务边界 |
| 关键词命中被称为相似检索 | 会造成专业能力误解 |
| 检索一次即结束 | 无法处理覆盖不足、冲突结果和用户要求深入 |
| 只传历史问题文本 | 无法形成可验证的任务记忆和结果集指代 |
| 五个最小对象被视为完整领域模型 | 缺少会话、目标、确认事实、结果集、计划、证据充分性和恢复状态 |

### 4.4 D 类：必须补充业务定义

首要咨询目标、各目标必要信息、自主工具调用的确认边界、允许迭代检索的范围、证据充分性与停止条件、人工复核触发条件、质量指标和阈值、数据覆盖与允许来源、风险措辞、会话保留与继承、目标用户/服务渠道、专业验收集和责任人，均不能由 Codex 自行决定。

## 7. 用户任务与智能体行为缺口

### 7.1 当前缺少统一任务成功定义

原始需求以模块为单位定义得较细，但没有统一说明：用户说出一个业务目标后，什么结果才算完成。例如“帮我判断这个技术方向有哪些接近专利，并比较最相关的两项”同时需要理解、澄清、检索、筛选、取证、比较和解释；当前各模块合同没有把这一目标串成一个产品级完成条件。

### 7.2 当前缺少主动规划政策

需要业务定义而非技术推定的行为包括：

- 何时直接执行，何时先问用户；
- 何时必须确认提取特征、对象或范围；
- 初次检索何时算覆盖不足；
- 何时自动调整检索条件，何时必须请求确认；
- 何时读取权利要求或更深证据；
- 中间结果冲突时如何呈现和继续；
- 用户否定特征后哪些结果失效、哪些上下文仍可复用；
- 目标中途变化时是延续任务、分支任务还是新建任务；
- 什么时候任务完成、阻塞或需要专业人员。

当前固定顺序不是业务约束，而是开发实现。权限、法律结论和人工决定边界应保留；“只能一次调用”“必须跳页面”“用户手工选择所有工具”不应成为最终产品规则。

| 特征提取/编辑/确认 | 明确要求 | 覆盖单一样例 | 独立工作台覆盖，统一对话未持久闭合 | 用户修正不能成为后续任务事实 |
| 关键词召回 | 要求 | 简化 | 字面包含 | 可运行但容易漏召回 |
| 语义召回 | 要求 | 排除 | 无 | 同义、近义和技术表达变化难以召回 |
| 混合检索 | 需求目标可推导，具体策略需确认 | 排除 | 无 | 不能兼顾精确词与语义覆盖 |
| 重排 | 原始需求提及 | 排除 | 固定加权排序 | 顺序不代表专业相关性 |
| 查询过滤 | 日期、分类、地域等 | 部分 | 后端较多，前端日期缺失、地域仅 CN | 用户无法完整控制范围 |
| 多候选 | 要求 | V0 曾排除号码多候选 | 可返回多条 | 数量存在不代表候选质量成立 |
| 证据片段/权利要求 | 要求 | 合成定位 | 有摘要/权利要求文本路径 | 片段选择质量和覆盖未验收 |
| 原文查看 | 要求 | 弱化 | 咨询抽屉仅元数据 | 用户无法就地核验 |
| 重新/深入检索 | 要求条件调整与新任务 | 排除 | 依赖用户手工重新提交 | 智能体不会根据不足主动继续 |
| 召回与排序评价 | 需要专家集 | 明确排除 | 无业务验证 | 不能证明好用 |

`Recall@K`、排序质量、数据覆盖和任务成功率均应纳入验收，但目标值和通过线必须标记为 **待业务/专业人员确认**。

## 9. 对话能力缺口

原始需求定义的不是纯聊天界面，而是任务型对话。当前实现与目标的差异如下：

| 能力 | 当前状态 | 缺口 |
| --- | --- | --- |
| 多轮上下文 | 仅上传历次用户问题文本 | 没有答案、工具结果、确认事实和证据状态 |
| 指代消解 | 无可持久引用的结果集 | “第二条”“刚才那个”不能可靠解析 |
| 用户纠正 | 可再发一句话 | 不知道纠正哪个槽位，不记录覆盖和影响范围 |
| 技术方案修改 | 重新解析文本 | 不能标记旧检索/比较结果因何失效 |
| 对象切换 | 可能重新识别另一意图 | 没有对象栈或明确的继续/分支语义 |
| 信息缺失 | 固定契约生成补问 | 尚不能基于任务风险判断是否真的必要 |
| 信息冲突 | 原始解析器有局部规则 | 缺少跨轮、跨工具冲突处置政策 |
| 已确认信息 | 未形成统一会话事实 | 可能重复索取或丢失确认 |
| 工具结果进入后续对话 | 前端未回传 | 后续问题不能可靠建立在真实结果上 |
| 回答后继续追问 | UI 可继续输入 | 只是新请求，不是同一任务的状态延续 |
| 用户改变目标 | 没有任务级政策 | 不会明确保留、作废或重用哪些上下文 |

因此，当前有连续聊天外观，但不具备完整任务型对话语义。

## 10. 证据与可信度缺口

应继续保留的良好基础包括：权限边界、来源/版本追踪、失败与无结果分离、用户确认、不可变版本、人工作最终决定、候选引用白名单和候选文本提示注入隔离。

仍存在四类缺口：

1. **证据深度**：来源抽屉只有 ID、版本和定位，用户不能直接核对受控原文、原始 URL 或内容摘要。
2. **充分性**：系统验证“引用在候选白名单中”，但没有判断这些候选是否足够回答用户问题。
3. **冲突处理**：没有定义多个来源互相冲突时的优先级、披露和继续检索行为。
4. **可信度表达**：固定“仅供技术参考”是必要边界，但不能替代对未知、缺失、覆盖范围和不确定性的逐项说明。

引用白名单能防止模型凭空引用列表外来源，不能证明候选本身正确、完整、最新或足以支撑结论。

## 11. 业务验收缺口

### 11.1 应建立的任务级质量维度

| 维度 | 要评价的问题 | 目标值/通过线 |
| --- | --- | --- |
| 任务完成率 | 用户目标是否完成，而非接口是否返回 | 待业务/专业人员确认 |
| 必要追问质量 | 是否只问必要问题，是否漏问风险关键项 | 待业务/专业人员确认 |
| 纠正恢复能力 | 用户纠正后是否正确更新事实并重规划 | 待业务/专业人员确认 |
| 检索召回质量 | 相关文献是否进入候选集 | 待业务/专业人员确认 |
| 排序质量 | 高价值候选是否出现在合理位置 | 待业务/专业人员确认 |
| 证据支持率 | 答案中的实质陈述是否有充分证据 | 待业务/专业人员确认 |
| 来源可核验率 | 用户能否访问并定位所引内容 | 待业务/专业人员确认 |
| 无依据回答率 | 是否出现候选证据不支持的陈述 | 待业务/专业人员确认 |
| 失败解释质量 | 是否区分无结果、无权、源失效、模型和工具故障 | 待业务/专业人员确认 |
| 多轮任务连续性 | 追问、纠正、换对象后是否保留有效上下文 | 待业务/专业人员确认 |

### 11.2 当前不能通过的验收推论

- 页面显示候选，不等于候选与用户技术方案相关。
- 模型真实调用，不等于模型答案正确。
- 引用通过白名单，不等于证据充分。
- API、数据库记录和任务状态存在，不等于用户目标闭环。
- 自动化测试通过，不等于专业人员认可检索、比较或风险表达。
- 当前统一门禁本身仍有失败，且大量浏览器用例使用预制响应；详见 `docs/30`。

## 13. 咨询智能体完整产品能力基线

本节描述目标产品应是什么，不指定 Java、API、表、Runtime 或 Workflow 实现。

### 13.1 核心用户任务链

```text
用户用自然语言说明业务目标
-> 智能体识别目标、对象、约束、风险和信息缺口
-> 只提出完成任务所必需的澄清问题
-> 在风险需要时展示提取/推导的关键事实供用户确认
-> 规划并执行已授权的检索、查询和资料读取步骤
-> 评价覆盖范围、结果冲突和证据充分性
-> 必要时调整条件并继续检索或读取更深证据
-> 允许用户查看、选择和纠正候选及证据
-> 输入满足条件时执行用户要求的技术对照
-> 生成有范围、证据、不确定性、限制和下一步的回答
-> 接受追问、纠正、对象或目标变化，并在保留有效上下文的前提下重规划
-> 达到约定条件时建议或进入专业人工复核
-> 仅在任务完成、明确阻塞或用户停止时结束
```

### 13.2 完整产品行为基线

| 能力域 | 目标产品行为 |
| --- | --- |
| 用户入口 | 用户无需理解模块、工具或页面结构即可表达完整目标 |
| 目标理解 | 区分目标、对象、事实、约束、风险和未知，不把模型推测写成确认事实 |
| 追问 | 只追问影响执行或风险的必要信息，已确认内容不重复询问 |
| 计划 | 在授权范围内选择、排序、重复或停止能力调用；高风险动作按业务规则请求确认 |
| 检索 | 支持适合场景的关键词、语义或混合召回、过滤、重排和结果解释 |
| 深化 | 初次覆盖不足或证据冲突时，能说明原因并按政策继续检索或取证 |
| 对话状态 | 保存目标、确认事实、结果集、选择对象、工具结果、证据和未决项 |
| 纠正与变更 | 用户更正后保留历史版本，重算受影响步骤；目标变化时明确延续、分支或新任务 |
| 对照 | 对输入和证据满足条件的候选执行可解释的逐项技术对照，不越界作法律结论 |
| 答案 | 区分事实、工具结果、模型总结、不确定性和建议；实质陈述可追溯 |
| 来源 | 提供可核验来源、版本、定位、允许的原文/链接和失效说明 |
| 异常 | 区分无结果、无权、来源失效、配置问题、模型故障和工具故障，保留可恢复进度 |
| 人机协作 | AI 提取、检索、归纳和草拟；授权人员作正式专业或业务决定 |
| 结束 | 完成、证据不足阻塞、需要人工复核或用户停止均有明确状态和原因 |
| 质量 | 使用业务任务集和专业标注评价，不以技术链路指标替代 |

该基线是完整目标，不是下一迭代承诺。阶段划分只能决定实现顺序，不能缩小最终产品目标。

## 15. 当前阶段不应修改的内容

在上述决策和正式设计证据完成前，不应：

- 修改 `requirements/` 或把本报告结论伪装成原始需求结论；
- 升级任何正式需求 D/V/A 状态；
- 新增通用 Agent Runtime、Workflow 平台或统一三域运行时；
- 先行扩展数据库模型、业务 API 或大规模重构架构；
- 用现有代码能力反向缩小目标产品；
- 自行设定 Recall@K、Precision、任务成功率或专业通过线；
- 把字面匹配重命名包装成语义或专业相似度；
- 扩大执法和裁决实现范围。

执法与裁决未来很可能出现同类问题：固定流程代替自适应协助、上下文不连续、证据充分性未定义、只验链路不验任务。当前只记录风险，不在本报告设计其完整产品。

## 17. 对用户指定 12 个问题的明确回答

### 17.1 当前原始需求本身是否存在明显产品缺口？

**存在，但不是能力列表过少。** 缺口主要是跨模块的统一任务成功定义、主动规划与重规划、证据充分性、冲突处理、停止条件、人工升级政策和可执行的业务质量验收。

### 17.2 当前 V0 是否过度限制了最终智能体能力？

**是。** V0 本来是单一技术闭环验证，却长期把单意图、固定目的、一次调用、最小上下文和开发数据固化为当前产品形态。

### 17.3 哪些 V0 限制应该保留为纯技术验证限制？

合成数据/内存仓储的第一轮验证、不接真实 SSO、不做正式人工流程、不建通用 Runtime/Workflow、校准前不输出数值评分、不做外部写回和不预建跨域大模型，应作为隔离技术风险的开发限制保留其历史定位。

### 17.4 哪些 V0 限制不能继续作为最终产品限制？

单一意图、固定技术参考目的、固定一次工具序列、用户手工选择全部下一步、关键词匹配冒充相似能力、检索一次即结束、只传历史问题文本，以及把最小对象模型当成完整产品模型。

### 17.5 哪些能力当前代码真实存在但能力较弱？

外部模型意图候选、本地公开专利真实检索、模型基于候选证据生成答复、候选引用白名单、来源 ID/版本复查、特征提取准备、单消息多意图和专利/商标/案例分路由均真实存在；但检索、上下文、证据深度、配置可复现性和专业效果较弱。

### 17.6 哪些能力当前代码实际上不可用？

真正的多轮任务对话、结果集指代、持久确认槽位和对象状态、用户纠正后的重规划、自主迭代/深入检索、语义或混合专利检索、专业相似检索、普通用户专利对照闭环、咨询内原文核验、真实身份权限和业务/专业验收尚不可用或未成立。

### 17.7 为什么用户会觉得当前智能体“不好用”？

因为系统能“识别并调用一次工具”，却不能持续理解用户想完成的任务；它会丢失答案和结果上下文，不会根据弱结果主动继续，不会可靠处理“第二条”或用户纠正，比较需要跳页且可能被阻断，检索又主要是字面匹配。用户承担了选择工具、判断结果是否充分和组织下一步的工作。

### 17.8 真正好用的咨询智能体核心用户任务链是什么？

自然语言目标 → 必要澄清与高风险事实确认 → 授权范围内规划并执行检索/查询 → 评价覆盖、冲突和证据充分性 → 必要时迭代深化 → 用户查看/纠正候选 → 有条件地执行技术对照 → 输出带证据、范围、不确定性和下一步的回答 → 接受追问/纠正/目标变化并重规划 → 完成、明确阻塞或人工升级。

### 17.9 当前代码距离核心任务链还缺哪些关键产品能力？

缺持久任务状态、确认事实和结果集、目标变化语义、动态工具计划、覆盖/证据充分性判断、迭代检索、冲突证据处理、原文核验、对照闭环、人工升级产品行为和任务级质量验收。

### 17.10 哪些是需求、V0、实现和验收问题？

需求问题是统一行为政策与质量定义缺失；V0 问题是临时收缩被固化；实现问题是无持久上下文、固定路由、字面检索和比较断链；验收问题是没有业务任务集、专业标注、质量阈值和无伪响应的可复现真实闭环。

### 17.11 修改代码前哪些需求必须由业务人员确认？

首要任务与完成定义、必要信息、自主调用和确认边界、迭代检索/停止规则、允许数据与覆盖、证据充分性、冲突处理、人工升级、会话保留、风险措辞、质量指标/阈值、评测集和责任人。

### 17.12 哪些现有能力应保留，哪些只是开发期实现？

应保留权限边界、来源/版本追踪、失败与无结果分离、用户确认、不可变版本、人工作最终决定、候选引用白名单和提示注入隔离。固定意图兜底、固定 `switch`、一次检索、字面权重、固定模板、开发身份、PUBLIC_LOCAL/合成适配器、只传历史问题和页面跳转式编排都只能视为开发期实现，不能继续定义最终产品能力。

## 18. 最终审查结论

原始咨询需求已经包含大量正确的目标能力，不能以当前弱实现为理由重写成“关键词检索 + 单轮聊天”。同时，这些需求尚未把分散模块组织成一个统一、可验收的自适应用户任务政策。V0 的技术验证边界本身大多合理，问题在于它们事实上塑造并限制了当前产品。

因此，本轮结论不是“立即重写代码”，而是：**先恢复完整产品目标，补齐必须由业务和专业人员决定的智能行为与质量合同，再据此判断现有代码哪些保留、哪些调整、哪些重新设计。**
