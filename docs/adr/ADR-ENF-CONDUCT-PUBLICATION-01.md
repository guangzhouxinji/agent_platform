# 行为规则发布样例与案件抗辩复核分离

日期：2026-10-03。责任：Codex技术实施；项目用户在本会话明确授权最小冻结发布契约兼容修正。关联主计划 FIX-ENF-CONDUCT-PUBLICATION-01 / IMP-ENF-DOCUMENT-DRAFT-05；不重新开D，不修改requirements。

## 来源与问题

requirements/知识产权执法助手/10-侵权行为分析规则配置需求文档.md 第4、5、7节要求按要件、依据完整性发布、保留缺失输入，失效或范围不匹配不得发布；11-侵权行为分析需求文档.md 保留抗辩待核实与辅助意见。59轮保留的组件反例证明：含已配置抗辩的规则，评估器有/无defenseRefs均保留抗辩待复核缺项，而原发布要求正例零缺项，导致合法配置无法发布。

## 最小技术修正

只改 ConductRuleService.verifyExample 的发布样例分类，不改输入模型/API/DB/评估器/报告/审核/权限/法律依据门禁。

- 有非空抗辩标准且noDefensesConfirmed=false时，DEFENSE_UNASSESSED或DEFENSE_REVIEW_REQUIRED是评估器固定生成的待人工复核输出。发布正例可明确预期该输出，但必须真实匹配评估器的全部gaps与INSUFFICIENT结果；不可删除缺项或改称SUSPECTED。
- 发布正例仍须无要件、权利、依据等其他缺项；配置本身仍需完整来源、抗辩标准及当前批准范围。
- 发布负例必须保留至少一个上述待复核项之外的缺口，不能仅换一个抗辩引用便充当负例。
- 无抗辩已确认规则保持原零缺项正例门禁；空抗辩未确认/缺确认来源/矛盾配置仍拒绝。
- 所有例子仍精确匹配ruleId、版本、行为、outcome、全部gap集合、唯一指纹；失权、未批准依据、状态/CAS/幂等与事务不改变。

这是规则配置验证与真实案件最终判断的分离，不是确认抗辩不成立，不是法律效力批准，也不是专业业务验收。历史59轮反例和失败XML不改写。真实CNIPA规则缺少来源/适用核验时仍保持DRAFT/REVIEW_REQUIRED；技术受控规则只能用于明确标记的验证，不能当公开案件规则消费。
