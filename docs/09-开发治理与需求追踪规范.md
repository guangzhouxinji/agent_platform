# 开发治理与需求追踪规范

版本：V1.4
日期：2026-10-06

## 1. 目的与主线

治理只用于保护以下开发主线，不成为独立项目：

```text
原始需求 -> 当前 MVP -> 领域模型 -> Task -> 代码 -> 测试 -> 真实验收
```

一个事实只维护一次。实施顺序、当前工作包与最终交付标准统一见 `docs/08-总开发实现计划.md` 第0节；`docs/00`仅为导航。

## 2. 信息性质

| 类型 | 判定 |
|---|---|
| 原始业务需求 | 可定位到 `requirements/` 原文，不得改写其含义 |
| 已确认业务决定 | 有来源、责任人/系统、日期、范围和明确结论 |
| 技术设计 | 为满足需求选择的可审查实现方式，不声称来自原文 |
| 技术假设 | 为继续可逆工作而暂用，必须注明验证条件和影响 |
| 待确认事项 | 缺少业务、法律、权限、数据或外部系统事实，登记在 `docs/02` |

## 3. 最小追踪链

每项需求只维护一行端到端证据：

```text
原需求 -> 关键契约 -> 设计 -> API/数据 -> 代码 -> 测试/偏移检查 -> 真实验收
```

`docs/08` 是人工维护的状态唯一来源；`docs/project-plan.json` 是由它生成并校验的唯一机器运行数据，禁止手工修改；HTML 只读取 JSON，不保存或内嵌任务状态。契约保存关键约束，不保存项目进度；测试和验收记录保存结果，不另建总状态台账。

## 4. 开发准入

业务 Task 开始前必须满足：

- 有稳定 Task ID、关联需求、当前 MVP、依赖、退出条件和负责人。
- 原需求摘要未变化，关键契约能定位原文。
- 输入、输出、来源、权限、状态、AI/Rule/Human 边界和当前 Task 的 V0/真实样例足够明确；固定真实样例、专业阈值和验收人只作为正式效果验证与验收的前提。
- 影响本 Task 的待确认项已关闭，或明确限定为不含业务语义的可逆技术工作。
- 设计证据说明每项新增业务行为来自原需求或已确认决定。
- 产品代码和接口必须直接实现最终合同；获准替代数据只替换输入，不能替换权限、规则、状态、流程、结果或异常行为。历史开发专用窄D不构成最终产品编码准入。

任一项不满足，禁止编写对应业务 API、迁移和代码。AI 不得根据类似功能猜测角色、状态、法定条件、阈值、期限、数据授权或验收结果。

## 5. 完成判定

| 状态 | 必须具备 |
|---|---|
| 已实现 | 最终合同对应的代码与必要配置存在；关联需求和当前D可追踪；Mock、Synthetic、Fixture、固定候选或TODO行为不计产品实现 |
| 已验证 | 关键 MUST 已测试、MUST_NOT 未违反、无来源新增行为为 0、证据链接有效；真实与模拟范围分开 |
| 已验收 | 业务负责人使用约定真实样例确认结果；环境、版本、差异和未满足项有记录 |

代码写完、接口返回、页面可操作或模型给出答案，都不能单独证明需求正确。历史开发期限定实现和测试只保留为其当时范围的技术证据，不自动迁移到最终产品实现/验证/验收状态；当前最高优先级口径见docs/08第0节与docs/02第37节。

### 5.1 单人团队的开发期证据复核

开发期 Component/Contract 修复不以第二名开发者签字为必要条件。修复与复核仍分两步：先固定设计条款、失败反例和通过条件；修复后重新运行原反例、新增负向测试及受影响模块回归，并从代码反查命令入口、状态/权限/版本边界和审计输出。复核记录须列出测试命令及结果、逐项条款结论、未覆盖项和真实/模拟范围；发现新的 P0/P1 或测试失败时不得释放依赖任务。只有证据均满足既定退出条件时，才标记“开发期契约验证通过”。

同一人可以执行上述两个步骤，但不得只凭自己写的测试通过就宣称专业正确、真实集成或业务验收，也不得把这类复核称为“另一名人员独立复验”。正式资料、实际权限、法律/专业判断和政府人员验收仍按各自门禁与外部证据办理。

## 6. AI / Rule / Human 边界

- AI 只做理解、抽取、分类、总结、候选分析和草稿。
- Rule/领域代码只执行已确认的确定性条件，不创造法律规则。
- 权限由可信授权机制判断；AI 不授予权限。
- 人工或权威系统负责事实确认、证据采信、正式审核、处罚、裁决、签发和正式状态。
- Agent 只编排已批准能力，不直接写权限、审核决定、正式状态或中心源记录。

## 7. 轻量检查

变更原需求状态、关键契约、计划证据或业务实现前后运行：

```text
node scripts/verify-all.mjs
```

检查器先从 `docs/08` 生成 `docs/project-plan.json` 和 HTML，再检查需求摘要、41 项唯一台账、契约来源、证据链接、依赖图、READY、关键路径、计划健康度、实现证据和状态越级。它不证明法律或业务语义正确；语义正确性由原文反查、固定样例测试和真实业务验收共同证明。

每轮只报告：涉及需求、状态变化、未覆盖 MUST、MUST_NOT 违规、无来源行为、待确认项、真实/模拟范围、下一步。不得为同一结果再生成多套 Gate、Trace 或 Review 总报告。

### 7.1 持续执行循环

每次新执行回合按同一顺序推进：

```text
读取 docs/08 与 project-plan.json
  -> 运行计划健康检查
  -> 读取自动计算的 READY 队列
  -> 优先选择 READY 中的结构关键路径任务
  -> 从自动并行评估中选择无依赖、模块和独占资源冲突的任务
  -> 连续实现相关任务
  -> 测试、修复、回归
  -> 先更新 docs/08
  -> 重新生成 JSON 与 HTML
  -> 再次校验并继续下一个 READY
```

正在执行的主任务不重复列为 READY。READY 为空但存在进行中任务时继续完成该任务；只有真实阻塞、必须的人工决定、阶段退出条件需要外部验收，或没有可执行任务时才停止。人工填写的“可并行”只作提示，最终展示以依赖、模块、资源和 Gate 自动判断为准。

## 8. 变更控制

- `requirements/` 只读；文件增删或摘要变化时立即停止受影响工作并报告基线变化。
- 已确认业务决定变更时，更新 `docs/02` 的证据，再评估契约、设计、代码、测试和验收影响。
- 技术决定可用 ADR 记录；不得表述为原需求或已确认业务事实。
- 模拟、静态、stub 或 TODO 行为不得标记为已实现、已验证或已验收。

### 8.1 2026-10-05 Agent化增量重构证据边界

用户明确调整优先级后的重构任务仍只登记docs/08；不重开冻结任务，不新增平行状态台账。共享机械内核的组件/磁盘恢复测试不等同三领域正式接线、生产DM8恢复、真实模型或业务Task级Golden评测。每个Agent独立持有Definition/Skill/Tool/Prompt/Policy/Evaluation；结构检查拒绝Agent间实现依赖及kernel对领域/框架/持久化/HTTP实现的依赖。结构通过不证明语义/法律正确。全量测试的原始失败与环境前置缺口保留，定向通过不得覆盖或冒充全量绿色。

## 8.2 唯一实施文档与连续执行（2026-10-06）

用户明确要求收敛全部实施计划。docs/08第0节是从当前起点到41项交付的唯一现行路线，7.8.3是唯一任务状态表，第8节是唯一需求证据账本。现有P阶段和逐项R/D仍保留，不因路线重新编排自动放行。旧提案、历史“下一步”和旧阶段播报只保留作历史，不参加调度。

不再创建另一份实施文档、工作包总状态表或新一轮“全量重构计划”。完成任务后按08路线选择下一个满足依赖的任务；若受阻，记录影响范围、责任人和解除条件，继续其他已获准工作。结束当前批次须给出下一具体动作及前置，不只写“继续完善”。

verify-all非零不一概等于所有工作停止：需求基线变化必须停止；本次回归先修；未决业务分支保持门禁；既有无关环境问题保留全仓红灯并安全隔离恢复。未知失败须先定位，不直接豁免。分支结果、受影响回归、全仓结果分别报告；总脚本提前退出时不可宣称后继检查均已执行。

原始需求、现行设计、docs/02决定和旧验证原件不是冗余计划，不为减少文件数而丢弃。迁移先保存原始字节/SHA并修复引用；可恢复归档只记录原日期事实，不维护状态。禁止向文件头持续追加日报。
