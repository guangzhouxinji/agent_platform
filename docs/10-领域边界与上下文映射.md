## 1. 文件定位与评审范围

本文件是基于原始业务需求形成的领域边界设计，不是新的业务事实来源。业务事实以 `requirements/` 为准，人工确认结论以 `docs/02-待确认事项清单.md` 及其证据为准。

ARC-03 只确定三类助手的职责、数据使用关系、辅助分析与正式决定的分界，以及跨领域复用边界。本阶段不冻结具体角色、权限、DataScope、状态枚举、字段、API、数据库、Runtime、部署单元或产品选型。

文中信息按以下性质使用：

| 标记 | 含义 |
|---|---|
| 原需求边界 | 可由原始需求直接支持的职责或限制 |
| 设计边界 | 为防止职责混淆而作的架构划分，不新增业务行为 |
| 待确认 | 原始需求不足以确定，必须由业务方或权威系统负责人提供证据 |
| 技术候选 | 后续可评估的实现方式，不是业务概念或既定方案 |

## 2. 三个业务领域的最终边界

| 领域 | 核心职责 | 明确不负责 | 输入 | 输出 | 权威数据来源 |
|---|---|---|---|---|---|
| 咨询 | 管理本次咨询的问题与必要补问；发起授权检索；比较候选信息；生成带来源定位的辅助分析和回答 | 不维护权威知识源；不决定数据权限；不把 AI 回答认定为正式专业意见；不替代需要的人工复核 | 用户问题、用户获授权提供的资料、中心知识查询结果 | 检索候选、资料缺失或冲突提示、辅助分析、带来源定位的回答 | 商标、专利、案例、法规等中心知识服务；具体权威系统和稳定引用方式待确认 |
| 执法 | 管理本次线索处理的本地工作记录；保留原始线索与解析/修订版本关系；整理执法语境下的证据关系和证据链；形成辅助分析并衔接人工审核 | 不改写中心权威线索、案件或证据；不自动采信证据；不作正式违法认定、处罚决定、签发、送达或执行 | 获授权的线索、案件/权利信息、证据、法规和已确认规则 | 线索解析版本、证据链整理结果、证据或规则缺口、辅助分析、针对该分析版本的人工审核记录 | 中心线索、案件、证据、权利和法规系统；各类数据的具体所有者待确认 |
| 裁决 | 管理本次案件分析的本地工作记录；固定本次使用的材料/事实版本；进行法规、专利知识和证据的辅助分析；生成报告草稿并衔接人工复核 | 不改写中心正式案件状态；不作正式裁决；不承担签章、送达、办结或归档 | 获授权的案件及材料、事实版本、法规、专利知识、证据和报告模板 | 法规/知识匹配结果、辅助分析、来源定位、报告草稿及针对确切版本的人工复核记录 | 中心案件/流程、法规、专利、证据、模板及正式签发系统；具体所有者待确认 |

以上三个领域是业务责任边界，不等同于技术架构层、Java Module、微服务或部署单元。41 项需求的主归属仍以 `docs/04-原需求功能归并矩阵.md` 为准，本文件不重复维护需求清单。

## 3. 上下文映射与数据所有权

### 3.1 权威数据与本地工作结果

| 数据类别 | 边界结论 | 其他领域可做什么 |
|---|---|---|
| 中心知识数据 | 本项目不是商标、专利、案例、法规等权威内容的所有者 | 在授权范围内查询、引用或使用可追溯快照；不得静默改写来源事实 |
| 中心案件数据 | 正式案件记录及正式状态由待确认的中心权威系统拥有 | 裁决域及获授权的执法流程可引用；本地工作进度不得冒充正式案件状态 |
| 中心线索数据 | 原始线索及中心登记结果由待确认的中心权威系统拥有 | 执法域可保存来源引用及本地解析/修订版本；回写和回执责任待确认 |
| 中心证据数据 | 原始证据、来源和中心登记记录由待确认的中心权威系统拥有 | 获授权领域可引用或使用获授权快照；采信含义、证明目的和正式效力由具体业务流程决定 |
| 咨询工作结果 | 咨询域拥有本次问题、检索选择、辅助分析和回答版本的业务语义 | 其他领域如需使用，只能引用明确版本，不得把咨询回答直接当作执法或裁决结论 |
| 执法工作结果 | 执法域拥有线索解析、证据关系和辅助分析版本的业务语义 | 其他领域只能引用明确版本；人工审核不自动变成正式处罚或裁决结果 |
| 裁决工作结果 | 裁决域拥有案件分析和报告草稿版本的业务语义 | 其他领域只能引用明确版本；复核通过不自动等同签发、送达、办结或归档 |

本地是否可以缓存、落库、索引或送入模型，属于数据使用授权问题，仍由 `P0-03` 控制；本文件不以技术需要推定授权。

### 3.2 跨领域交互原则

- 领域间交换来源引用、明确版本和已授权的结果，不共享可被任意领域改写的业务记录。
- 一个领域使用另一个领域的结果时，必须保留结果所属领域、来源和版本；使用方自行负责其业务语境下的采用判断。
- 中心写入、状态推进和正式回执必须通过权威系统边界；在责任和接口未确认前，只能保留本地辅助结果，不能假定回写成功。
- 领域间直接联动的具体流程、事件和同步方式待真实业务流程确认后设计；ARC-03 不预设事件总线、共享数据库或跨域状态机。

## 4. 跨领域共享与必须独立的内容

### 4.1 可以共享的能力

下列内容可以作为平台技术能力复用，但复用不改变业务所有权：

- 对权威来源进行授权访问、保留来源标识、版本和可核验位置。
- 文件读取、检索、模型调用、技术任务执行、日志、审计和运行追溯。
- 人工处理记录的通用技术承载，例如记录处理对象版本、意见、处理人和时间；具体业务含义仍由各领域定义。
- 引用展示和来源失效检测；引用是否构成回答依据、执法证据或裁决依据，由所属领域判断。

身份接入、权限校验和 DataScope 执行可以采用共享技术能力，但具体授权规则、角色和数据范围不是共享平台自行定义的业务规则。

### 4.2 必须保持领域独立的内容

- 咨询回答依据、执法证据关系、裁决中的事实/证据分析具有不同业务语义，不能用一个统一 `Evidence` 模型替代领域判断。
- 咨询复核、执法辅助分析审核、裁决报告复核不是同一种业务决定，不能因共用技术组件而合并责任或状态。
- 三个领域的业务规则、业务工作状态、内容完整性和验收口径分别归各自领域，不建立统一业务状态机。
- 证据采信、违法认定、处罚、裁决、签发、送达、办结和归档等正式责任不得跨领域共享，也不得下沉给 Agent、模型或通用平台能力。
- 中心权威数据不得因被多个领域使用而转为本项目或“共享域”所有。

### 4.3 共享模型的评审结论

原始需求能够支持的跨领域稳定语义，仅限于“能够识别来源、固定所用版本并定位到可核验内容”。是否最终实现为 `SourceRef`、`VersionRef` 或其他结构，留待后续设计，不在 ARC-03 冻结。

以下名称均降级为技术候选，不作为已确认的跨领域公共领域模型：

| 候选名称 | ARC-03 结论 |
|---|---|
| `Claim` | 是架构分析术语，原始需求未确认其为三个领域共同业务概念 |
| `Evidence` | 原始材料可共享引用，但证据关系、采信和效力必须由执法域或裁决域分别解释 |
| `Citation` | 来源定位机制可复用；引用的业务用途和效力不能统一 |
| `Review` | 技术记录能力可复用；咨询、执法、裁决中的复核对象、责任和后果必须分开 |
| `Task` / `RunRecord` | 属于执行和追溯的技术能力，不是业务领域或正式业务记录 |

因此 ARC-03 不建立新的“证据域”“审核域”“任务域”或“运行域”。后续技术设计只有在消除真实重复且不抹平领域语义时，才可抽取共享结构。

## 5. AI、规则、人工与权威系统的责任边界

| 主体 | 可以负责 | 绝不能据此自动完成 |
|---|---|---|
| AI / Agent / Workflow | 理解、抽取、分类、总结、候选检索、候选分析、生成草稿和编排获授权工具 | 权限决定、证据采信、正式法律结论、处罚、裁决、签发、送达、办结、归档或改写中心源记录 |
| 规则引擎/领域代码 | 执行已有证据支持、已确认并发布的确定性条件；输出可追溯的校验或候选结果 | 自行补造法律规则、法定条件、阈值、角色、权限、正式状态转换或最终决定 |
| 授权人工人员 | 核实事实、修订机器结果、判断材料是否采用、复核辅助结果并执行其获授权的业务动作 | 具体人员类别、职责分离和可执行动作尚未确认，不能由本设计预设 |
| 正式业务系统 | 提供权威数据、正式状态和真实回执；按已确认流程记录正式业务结果 | 具体系统所有权、写入接口及回执语义尚待确认，不能由本项目模拟或推定 |

“辅助分析”包括检索候选、材料抽取、关系整理、规则校验、风险或结论候选、解释和草稿。凡会产生证据采信、正式权利义务、处罚、裁决、签发、送达、办结、归档或中心正式状态变化的操作，均属于正式业务决定或其执行，不得由 AI 输出直接触发。

## 6. 三个 MVP 的边界一致性

| MVP | 与原始需求的一致性结论 | ARC-03 固定的终点 | 仍待确认但不改变本次领域划分的事项 |
|---|---|---|---|
| 咨询 | 一致：用户问题、必要补问、授权检索、来源核验、辅助答复和引用形成闭环 | 带来源定位的辅助回答；需要正式采用时进入人工复核 | 首批问题类型、真实样例、哪些回答必须正式复核 |
| 执法 | 有条件一致：必须从线索和证据出发，并保留人工控制点 | 经人工审核后保留的辅助分析版本；不扩写为正式处理结果 | 首批线索来源、人工审核后的业务终点、正式决定和回写责任 |
| 裁决 | 有条件一致：案件、材料/事实、法规/知识、辅助分析、报告和复核形成闭环 | 针对明确材料版本的报告草稿及人工复核记录；不等同签发或结案 | 首批模板实际需要的分析输入，尤其 `ADJ-07` 至 `ADJ-09` 的纳入范围 |

上述结论只证明 MVP 业务边界与原需求没有明显冲突，不代表已经具备详细设计、开发或业务验收条件。真实样例、数据授权、人工控制点和验收依据仍按 `docs/02` 与总开发计划执行。

## 7. 待确认的所有权与责任边界

以下仅列真正影响领域所有权或正式责任的 P0 问题；继续归入 `docs/02` 现有条目，不建立新台账：

1. `P0-02/P0-03`：知识、案件、线索、证据分别由哪个中心系统拥有；各领域可查询、保存快照、落库、索引、模型使用和保留到什么范围。
2. `P0-01/P0-09`：本地工作结果是否以及如何回写中心；哪个系统确认写入、状态变化和失败回执。
3. `P0-04/P0-09`：谁负责事实确认、专业复核、证据采信、正式决定、签发、送达、办结和归档；具体角色及职责分离尚不冻结。
4. `P0-08/P0-09`：咨询回答触发正式专业复核的边界是什么。
5. `P0-08/P0-09`：执法辅助分析经人工审核后的业务终点是什么，何时才进入正式处理流程。
6. `P0-08/P0-09`：裁决首批报告模板强制依赖哪些分析输入，以及复核与正式签发之间的责任分界。

中心 API 细节、DM8 参数、文件存储、批准模型、字段、状态名称、具体角色和 DataScope 虽会阻塞各自后续设计或实现，但不阻塞 ARC-03 的逻辑领域边界结论。
